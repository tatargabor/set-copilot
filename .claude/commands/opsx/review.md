Review an OpenSpec change's **plan** against the real code and the project's rules, after
`/opsx:propose` and **before** `/opsx:apply`. The cycle is
propose → **review** → apply → verify → archive.

**You do not judge the plan yourself.** You start two named agents **blind and in parallel**
— neither sees the other's prompt or output — then merge what they return into
`openspec/changes/<name>/review-findings.md`. Two independent viewpoints catch different
classes of defect; letting one read the other turns them into one viewpoint.

**Input**: an optional change name after `/opsx:review` (e.g. `/opsx:review speak-follow-tts`).
If omitted, infer it from the conversation only when unambiguous.

---

## Steps

### 1. Select the change

If no name was given and the context does not settle it: run `openspec list --json` and use
**AskUserQuestion** to let the user pick among changes that have a `tasks.md`. Do not guess
and do not auto-select.

### 2. Load the artifacts

```bash
openspec status --change "<name>" --json
```

Confirm proposal, design (if the schema has it), specs and tasks exist. If tasks are
missing, stop: the plan is not finished, suggest `/opsx:continue`.

Read proposal.md, design.md, tasks.md and every delta spec under `specs/`. Note whether
proposal.md declares the change review-exempt (docs-only, or a retro-spec of shipped
behaviour, per `.claude/rules/spec-adversarial-review.md`). If it does and tasks.md has no
code task, tell the user the review is optional and ask whether to run it anyway.

If `review-findings.md` already exists, this is a re-review: keep the previous rounds and
append a new `## Round N` section (step 5) rather than overwriting history.

### 3. Launch both agents — blind, in parallel

**Two Agent calls in a single message**, so they run concurrently and neither can see the
other:

- `subagent_type: adversarial-code-reviewer` — "where does this plan break against the real
  code?"
- `subagent_type: rules-conformance-auditor` — "which mandatory rule does it violate or
  omit?"

Give each the same prompt: the change name, the folder path
(`openspec/changes/<name>/`), and the instruction to read the artifacts there itself and
return its findings in its own output format. **Do not** paste your own opinion of the
plan, a summary of likely problems, or (on a re-review) the previous findings — any of
those anchors the reviewer and the review stops being blind. The agents' own definitions
already carry the discipline: real code over spec text, `path:line` evidence, "if there is
no real defect, say so", and a mandatory "checked and found OK" section.

One round only. The agents do not debate; you merge.

### 4. Re-verify every CRITICAL (cheap, narrow)

A CRITICAL blocks apply, so it must not be a hallucination. For each CRITICAL either agent
reports, open the cited `path:line` and confirm it says what the finding claims. If it does
not, downgrade or drop the finding and record why. Do not re-review the plan beyond this.

Where both agents report the same defect, merge them into one finding citing both.

### 5. Write `openspec/changes/<name>/review-findings.md`

English prose (code, file and requirement names verbatim). Shape:

```markdown
# Review findings — <change-name>

## Round 1 — <YYYY-MM-DD>

Reviewers: adversarial-code-reviewer (blind), rules-conformance-auditor (blind)

### Status
| ID | Severity | Summary | Status |
|----|----------|---------|--------|
| C1 | CRITICAL | ... | OPEN |
| M1 | MAJOR | ... | OPEN |
| m1 | MINOR | ... | OPEN |

### Findings
#### C1 — <title> (CRITICAL)
- **Source:** adversarial-code-reviewer | rules-conformance-auditor | both
- **Claim:** one sentence.
- **Evidence:** `path:line`
- **Failure scenario:** input → wrong outcome.
- **Fix:** what to change, in which artifact.
- **Status:** OPEN

### Rules verdicts
(the auditor's PASS / FAIL / N-A table, unchanged)

### Checked and found OK
- (adversarial-code-reviewer) ...
- (rules-conformance-auditor) ...

### Open decisions (the user's)
- ... or "none"
```

Markers are exact and uppercase, so a reader (or a later script) can count them:

- Severity: `CRITICAL` / `MAJOR` / `MINOR`.
- Status: `OPEN` / `RESOLVED` / `REJECTED`.
  - `RESOLVED` names where the fix landed: `RESOLVED — tasks.md 2.3, design.md "Risks"`.
  - `REJECTED` **must** carry a reason: `REJECTED — <why the finding does not hold or does
    not matter>`. A bare `REJECTED` counts as `OPEN`.
  - Rejecting or waiving a **CRITICAL** needs the user's explicit OK in this conversation;
    record it: `REJECTED — <reason> (user OK, <date>)`. You never waive a CRITICAL on your
    own judgement.

If neither agent found a real defect, say so plainly at the top of the round ("Review ran;
no real defect found in the plan.") and still include both "checked and found OK" lists — an
empty file is indistinguishable from a review that never ran.

### 6. Close

Report the counts (CRITICAL / MAJOR / MINOR) and the next step:

- **Any OPEN CRITICAL** → `/opsx:apply` is blocked. Fix it in the proposal/design/tasks/spec
  artifacts and mark it `RESOLVED`, or get the user's explicit OK to reject it.
- **OPEN MAJOR** → fix before apply unless the user decides otherwise; record the decision.
- **MINOR** → may become a task; does not block.
- **Open decisions** → the user decides; list them.

After fixes, a second `/opsx:review` is optional; when you mark a finding `RESOLVED`
yourself, cite the artifact change that resolved it.

---

## When not to run it

- Docs-only changes, and retro-specs that only describe already-shipped behaviour — the
  proposal must say so (see `.claude/rules/spec-adversarial-review.md`).
- A change with no spec artifacts at all.
